# 爱意存折｜日常感谢与每周回顾 PRD

- 版本：v1.0，2026-09-07。
- 状态：需求设计稿，待产品确认后开发；本文件中的新增能力尚未实现。
- 适用：独立的微信小程序版本；不改原 H5 产品。
- 需求来源：产品梳理第 5 点——让关系平稳时，也有轻松打开产品的理由。
- 配套：[邀请流程设计规范](../design/invitation-redesign-v1.md)。两个需求可以分别排期，感谢功能不依赖邀请页改版。
- 已确认范围：用户确认按“感谢记录、每周回顾、邀请页精简”三个模块完整规划，三个模块均写测试和验收要求。视觉稿及以下具体数值仍为建议默认值，不是当前线上事实。

## 1. 问题陈述（Problem Statement）

现有主流程为“我做了什么→对方审批加分”和“我有什么委屈→直接扣分→对方回应”。它能够记录行动与分歧，却缺少不求回报的正向表达入口；平稳的日子里，用户可能没有打开理由。受邀者还可能把使用理解为不断处理审批。

希望用户可以把感谢当作一份礼物发给对方，而不是申请分数；也可以在一周结束后，自愿回顾相处中的小事。是否帮助了双方，需要内测验证，不能根据分数、记录量或使用频次推断关系改善。

## 2. 解决方案与边界（Solution）

### 2.1 本期交付

1. 新增“今天想谢谢你”：双方均可提交感谢，立即共享，不计分、不审批；收件人可选“收到了”轻回应。
2. 新增“这一周，和你”：展示上一完整自然周的轻量回顾，双方各自自愿填写三个问题中的任意一个或多个。
3. 感谢和已发布的周回顾进入历史，沿用已有空间访问、内容检查、导出、删除与审计机制。
4. 沿用现有四个底部导航，不增加第五个导航；新增编辑及详情页面承接功能。

### 2.2 必须保留的现有规则

- 共同爱意分数仍为 0–100，默认分段不因本功能变化。
- 行动由对方通过、调整 +1/+3/+5 或驳回；原感受入口仍直接扣 −1/−3/−5。
- 受邀者仍可调整共同初始分数；后续手动调分仍需对方确认。
- 双方权限平等；“感谢”不用于兑换原谅、抵消扣分或证明已经修复。
- 退出/删除停止共享的规则不变，不为留存分析保留用户已经要求删除的亲密正文。

### 2.3 非目标

本期不做连续打卡、补签、排行榜、强制回应、自动加分、AI 评价关系、关系诊断、照片上传、公开分享私密正文、付费墙或聊天系统。周回顾不是心理量表，也不是争执裁决工具。

## 3. 用户故事（User Stories）

1. 作为已配对用户，我希望直接写一句感谢，让对方知道自己的用心被看见。
2. 作为感谢发起者，我希望不选择分数、不等待审批，避免把感谢写成交换。
3. 作为发起者，我希望有可选提示帮助起笔，但系统不替我生成对方没有做过的事情。
4. 作为发起者，我希望提交中不会重复生成记录，网络恢复后可安全重试。
5. 作为发起者，我希望区分“已经保存但刷新失败”和“没有保存”，不必猜测。
6. 作为收件人，我希望看到对方的原话，可以选择轻回应，也可以什么都不点。
7. 作为收件人，我不希望未回应的感谢变成红点、欠账或催促。
8. 作为任意一方，我希望我的轻回应不会改变分数，也不被解释为原谅。
9. 作为任意一方，我希望历史能单独筛选感谢，且不丢失已有行动和感受。
10. 作为任意一方，我希望知道周回顾对应哪几天，避免误解时间范围。
11. 作为忙碌的用户，我希望周回顾只写一个问题也能提交。
12. 作为任意一方，我希望写好后立即让对方看见，不必等对方也完成。
13. 作为任意一方，我希望未发布的草稿不被对方和运营看到。
14. 作为任意一方，我希望可以跳过一周，不收到羞耻、责备或断签提示。
15. 作为任意一方，我希望没有记录的那一周也可以写下回顾。
16. 作为任意一方，我希望过去发布的回顾能够查看，但不会因此恢复已关闭空间的访问。
17. 作为任意一方，我希望跨周、跨年或更换手机时，同一周不会重复发布多份回顾。
18. 作为用户，我希望导出自己的感谢、回顾和轻回应，不连带导出伴侣的正文。
19. 作为申请删除的用户，我希望本人正文、轻回应及关联标识都按既有流程清理。
20. 作为运营者，我希望了解功能是否被双方自愿使用，而不需要读取亲密正文。
21. 作为旧版本用户，我希望升级后仍能读取以前的记录，不因新增记录类型崩溃。
22. 作为感到不安全的用户，我希望随时找到现有退出与删除入口，产品不强迫我继续互动。

## 4. 信息架构与入口

| 位置 | 变更 | 规则 |
|---|---|---|
| 已配对首页 | 在“记录一件事”之后增加轻量文字入口“今天想谢谢你” | 不替代原加减分主入口，不自动聚焦、不弹窗 |
| 记录页 | 新增同级类型“感谢”，原“行动”“感受”保留 | 切换类型保留各自的会话草稿，互不串写 |
| 首页下方 | 上一周回顾入口“这一周，和你” | 最多一条轻提示，不进入“待我处理” |
| 历史“我们” | 增加类型筛选：全部／行动／感受／感谢／约定与调分／周回顾 | 与近一个月、近三个月、全部时间范围组合使用；查询在服务端执行 |
| 感谢详情 | 原文、作者、时间、可选轻回应 | 不展示已读倒计时、不催收 |
| 周回顾详情 | 周期、摘要、双方已发布回答、填写入口 | 先发布的人不被锁住内容；不显示对方私人草稿 |

未配对用户不进入记录编辑器；由现有访问门禁转到邀请流程。完成配对后可以轻提示“先存下一句感谢吧”，但必须允许“以后再说”，不能把首次提交作为使用门槛。

## 5. 功能 A：今天想谢谢你

### 5.1 编辑页

- 导航标题：`今天想谢谢你`。
- 一句解释：`不为加分，只想让你知道。`。
- 多行输入框占主要区域；提示：`今天哪件小事，让你觉得被在乎？`。
- 0–300 字计数；沿用当前文本长度校验口径，前后端一致，trim 后至少 2 字，最多 300 字。
- 三个可选起笔提示：“谢谢你替我分担了…”、“今天被你照顾到的一刻是…”、“有件小事，我一直记得…”。点击打开示例说明，不直接把示例当成有效内容发布。
- 编辑页主按钮：`预览这份感谢`；预览页展示完整正文，主按钮 `把感谢送给你`，副操作 `再改一改`。只有预览页的发送按钮真正写入；无分数选择、无图片、无强制标签、无必选心情。
- 有内容时返回，提示“这段话还没发送”，可继续写或离开；不使用阻止退出的循环弹窗。
- v1 草稿仅保存在当前运行会话，切页/短暂切后台保留；彻底关闭后可能丢失，不显示“已自动保存”。草稿不上传云端、不进入日志。账号/空间切换、退出和删除后立即清除。

### 5.2 发布与送达语义

1. 校验当前身份、有效成员关系、当前隐私版本同意。
2. 使用既有文本安全检查；通过后，在事务内再次核验成员/同意状态。
3. 原子写入感谢、幂等结果及最小化审计；不得改动共同分数。
4. 保存成功：`感谢已存好，对方打开爱折就能看见。`，进入该感谢详情，返回可到首页。此处不声称微信消息已送达。
5. 保存成功但刷新失败：`感谢已保存，页面稍后同步。`。清除已保存的草稿，保留查看/刷新入口，不提示再次提交。
6. 真正保存失败：保留内容；网络/超时可重试相同操作，确定性校验错误由用户修改后创建新操作。

v1 不新增感谢类微信推送。已有订阅通知模块保持原样，不自动消耗订阅额度；后续另行配置模板、用户授权及发送规则。

### 5.3 展示与轻回应

感谢卡片显示“对方的一句谢谢”或“我送出的感谢”、正文、发布时间，正文长时可进入详情。

- 收件人可点 `收到了 ♥`；确认后显示 `这份感谢，我收到了`。
- 作者看到 `对方回应了这份感谢`，不能显示“对方已原谅你”或推断关系状态。
- 未回应时不出现“未读”“待审批”“超时”，不纳入待办总数。
- 轻回应可不做；只有另一位有效成员可执行，只记录一次，重复点击/丢包重试返回同一结果；v1 不支持取消或多种表情。
- v1 发布后的感谢不编辑、不单条撤回；编辑/撤回需单独设计双方可见语义，现有个人数据删除渠道保留。发布前应提供预览和返回修改。
- 同样的文字可能在不同日被再次表达，不得仅凭正文永久去重；只对同一 operationId 重试去重。

## 6. 功能 B：这一周，和你

### 6.1 周期与资格

- 唯一时间口径：Asia/Shanghai，自然周周一 00:00 至下周一 00:00，左闭右开；数据库存 UTC 时间。
- 每周一 00:00 起，提供刚结束的一周回顾；在这一个星期日 23:59:59 前可以发布，跨过下周一关闭该周的新发布入口。
- 首页仅提示最近已结束的一周。历史已发布回顾仍可看；过期但从未发布的空白周不生成记录、不堆积待办。
- 某周与当前共同空间有效使用时间有交集即可参与；本周刚配对且上一周没有共同空间的用户看到“下周一，来看看我们的第一周”。
- 配对首周摘要只计算配对后产生的数据；展示“从你们相遇于爱折的那天开始记录”。不引用过去空间的数据。
- 没有行动或感谢也可以填写，不设置“必须先记满 N 条”的门槛。
- 每个用户在同一空间、同一周只能发布一次；由服务端时间与唯一键决定，更改手机时区/时间不影响规则。

### 6.2 页面与内容

顶部：`这一周，和你`，显示完整日期区间（跨年必须带年）。说明：`挑一个想说的就好，不必每题都写。`

可选的事实摘要只有两项：

| 摘要 | 精确定义 |
|---|---|
| 这一周留下 X 句感谢 | 该空间在周区间内创建、目前仍可访问的感谢数；包括双方 |
| Y 件用心被看见 | 在周区间内被批准且目前仍可访问的行动数，按 reviewedAt，不按 submittedAt |

不展示谁贡献更多、不展示本周扣分榜、不从这些数值生成“你们更相爱了”。两项都是 0 时显示 `平常的日子，也值得留一句话。`，不堆两张零值卡片。

三个问题，各自 0–300 字：

1. `这周，哪件小事让你开心？`
2. `还有哪件事，想和对方慢慢聊？`
3. `接下来，想一起做点什么？`

至少一项 trim 后达到 2 字才可发布；其余项允许留空，不用占位文本代填。先进入只读预览，主按钮 `把这一周存好`，副操作 `再改一改`。明确提示 `发布后，对方会看到你填写的内容。`

### 6.3 双方阅读规则

- 自己发布后立即共享；不需要另一方批准，不修改爱意分数。
- 另一方即使没有填写也可阅读，不能用“先回答才解锁”施压。
- 展示“我写下的这一周”“对方写下的这一周”；未发布的位置只用一句 `每个人都有自己的节奏。`，不暴露对方是否正在编辑。
- 不把周回顾自动转成扣分感受、加分行动或生效约定；需要处理的具体事情，仍由用户另行发起现有流程。
- v1 已发布回答不可覆盖；重复发布返回已有结果。过期后可阅读不可补交，页面显示 `这一周已经收好，新的话可以记在今天。`
- 首页 `这周先不写` 只收起本人本周提示；可在截止前从历史入口继续填写，不通知另一方。
- 不新建定时推送任务；页面按服务端当前时间判断本周资格，摘要按需查询。

### 6.4 历史与删除影响

周回顾属于双人空间历史，每个人的回答是独立记录。汇总页动态组合双方当前可访问回答，不复制另一方正文到自己的记录中。

摘要是“当前仍保留的数据”统计，删除后相应减少；不保存包含私密正文的永不变化快照。个人删除后，其周回答与轻回应一并清理；另一方自己的回答按既有保留规则处理，不能继续看到已清理的内容。

## 7. 实施决策（Implementation Decisions）

### 7.1 模块边界

| 模块 | 责任 | 可独立测试的接口 |
|---|---|---|
| 正向记录领域模块 | 创建感谢、轻回应、分数不变约束 | 合法操作与明确业务错误 |
| 周期与回顾领域模块 | 周区间、首周资格、发布截止、一次发布限制 | 输入服务端时间与配对时间，输出周期与资格 |
| 云端内容写入模块 | 鉴权、同意、检查、事务、幂等、频控与审计 | 新增感谢/回顾写入动作 |
| 查询与契约模块 | 新记录解析、游标筛选、摘要、双人回顾组合 | 严格判别记录类型，输出一致的 id |
| 前端编辑与展示模块 | 会话草稿、预览、保存状态、历史、入口 | 无副作用组件与业务 hook |
| 隐私生命周期模块 | 本人导出、贡献字段擦除、关闭空间访问控制 | 全集合/缓存不残留个人内容的验证 |

不增加独立账号体系，不改用新数据库，不为周回顾引入 AI 服务或内容向量库。

### 7.2 记录模型

沿用共同记录集合，新增两种判别类型；不新增另一套正文副本。以下为语义契约，不是可直接粘贴的数据库脚本。

| 类型 | 必要字段 | 可选字段与约束 |
|---|---|---|
| gratitude | id、coupleId、kind、authorId、content、createdAt、status=shared | acknowledgedBy、acknowledgedAt 成对出现；authorId/acknowledgedBy 沿用空间内成员角色，不新增公开 OpenID |
| weekly_reflection | id、coupleId、kind、authorId、weekKey、weekStartAt、weekEndAt、answers、createdAt、status=published | answers 包含 joy/talk/next 三个可选文本；至少一项有效；无伴侣正文副本 |

- weekKey 使用上海时区该周周一日期，例如 `2026-09-07`，不依赖客户端周数库。
- 周回答 ID 从“空间＋用户＋weekKey”稳定生成，或使用等效复合唯一约束；感谢 ID 继续沿用“用户＋operationId”模式。
- 新类型不包含 requestedPoints/effectivePoints，不向旧类型假冒 status=pending。
- 新增统一的“记录标题、摘要、待办资格”映射，避免把所有非行动类型都当作感受或约定。
- 前端解析每一种响应结构；缺少 id、错误 authorId、错误 answers 或未知 kind 不得无校验断言为合法记录。

### 7.3 API 语义契约

所有动作沿用现有云函数 envelope；数据库内部 _id 必须正规化为前端 id。

| 动作 | 输入 | 成功结果/核心限制 |
|---|---|---|
| submitGratitude | operationId、content | 感谢记录；分数不变 |
| acknowledgeGratitude | operationId、recordId | 更新后的感谢；非作者且有效同空间，重复操作不累加 |
| getWeeklyReview | weekKey | 周期、可发布资格、动态摘要、双方已发布回答；不得返回草稿 |
| submitWeeklyReflection | operationId、weekKey、answers | 本人已发布回顾；同周已经发布则返回已有记录及 alreadyPublished 标识，不覆盖 |
| listRecords | cursor、kindFilter、timeRange | 组合条件下的稳定游标分页；不能只对首批 100 条客户端过滤 |

写入顺序：身份/成员/当前同意校验 → 可复用幂等结果检查 → 频控与内容检查 → 事务内再次校验 → 内容＋最小审计＋幂等结果原子提交。重试不能多扣限额或多写记录。确定性内容错误不作为永久成功结果缓存。

索引至少支持“空间＋类型＋createdAt＋_id”历史查询、感谢周区间计数、已批准行动 reviewedAt 周区间查询、按空间/作者/weekKey 查周回答。唯一性只用于有明确唯一业务键的索引，普通历史索引不得设为唯一；上线清单逐条标明集合、字段、顺序及是否唯一。

### 7.4 边界、频控及错误

- 感谢建议每用户每空间滚动 24 小时最多 10 条；轻回应最多 60 次/小时；回顾提交最多 6 次/分钟且每周最多一份。成功的同 operationId 重放不额外计数。阈值通过配置可调，内测再评估。
- 修改/清空输入不允许把空字符串转换为合法值；超过字数时保留输入并定位提示。
- 文本检查拒绝：`这段话暂时无法发送，请调整后再试。`，不展示敏感命中详情。
- 网络异常：`刚刚没连上，写下的话还在，可以再试一次。`；若无法确定服务端是否已提交，重试必须复用 operationId。
- 成员退出、账号删除、隐私版本更新：阻止新写入，清空/遮蔽旧空间内容并进入现有访问门禁。
- “收到了”与个人删除并发时，删除后的用户贡献不得被迟到的轻回应重新写回。
- 摘要加载失败不应清空编辑中的回答；展示摘要暂不可用，提交仍需服务器确认资格。

### 7.5 隐私与兼容

- 本人导出包含本人感谢、周回顾及本人轻回应贡献；不得夹带对方正文、对方周回答或对方轻回应贡献。
- 清理任务扩展字段级擦除：本人在另一方感谢里的 acknowledgedBy/acknowledgedAt，以及本功能增加的审计身份引用；结合用户在具体空间的成员角色清理，不能跨空间仅按 partner-a/partner-b 批量擦除。
- 不增加分析正文采集；埋点不记录文本、称呼、邀请码、OpenID 或整份接口 payload。
- 分段导出、原始导出大小限制及免费渠道继续有效；新类型必须进入所有导出/删除/分页分支。
- 旧客户端对未知 kind 可能报错，因此先发布包含新类型读取兼容的客户端，再开放写入开关。后端新增动作默认关闭，确认测试账号兼容后按空间白名单启用。
- 回滚仅关闭新建入口，保留已写数据的读取、导出与删除；不得删除内测数据解决版本兼容问题。上线前确定最低兼容客户端版本，旧客户端由版本检查提示升级。

## 8. 测试决策（Testing Decisions）

测试以外部行为为准，不绑定内部 helper 名或实现顺序。沿用现有领域测试、云函数入口 mock、契约与隐私清理测试方式；新增模块均写测试，不用“本地纯函数全绿”代替云端与双手机验收。

| 编号 | Given / When | Then（验收结果） |
|---|---|---|
| G01 | 任意分数下提交感谢并轻回应 | 分数、分段、既有积分流水均不变 |
| G02 | 发布感谢，双方刷新 | 作者和收件人均看到一条记录；不进入任何待办计数 |
| G03 | 同一 operationId 连点/响应丢包重试 | 只有一条感谢、一份审计成功结果 |
| G04 | 作者、第三人或已退出者尝试轻回应 | 被拒绝；对方原数据未改变 |
| G05 | 接收者并发轻回应 | 最终只有一份回应时间/身份，不出现重复记录 |
| G06 | 保存成功但随后刷新失败 | 明确提示已保存；再打开仍可见且无重复 |
| G07 | 切换行动/感受/感谢、打开隐私再返回 | 草稿彼此隔离，分数选择不串入感谢 |
| W01 | 周日 23:59:59 与周一 00:00、跨年 | 周期按上海服务端时间正确切换，截止边界唯一 |
| W02 | 配对当周、上一周无共同空间 | 不可发布虚构的配对前回顾；下周正常开放 |
| W03 | 没有任何记录 | 可填写，显示温和空态，无负面评价 |
| W04 | 只写一题/三题/全空/超长 | 前两种可发布；全空和超长阻止提交并保留文字 |
| W05 | 同用户不同设备并发发布同周不同正文 | 只一份胜出，另一端读取已有结果，不能覆盖 |
| W06 | A 发布、B 没发布 | B 可读 A；A 不得读取 B 草稿；无互相解锁门槛 |
| W07 | 历史超过 100 条 | 摘要和感谢筛选覆盖全部符合条件的云端记录 |
| W08 | 删除贡献过的感谢或本人回顾 | 摘要及视图更新，不保留已删除正文快照 |
| P01 | 退出后继续调 API / 点击旧链接 | 无法读取对方内容；本人导出仍严格限定本人范围 |
| P02 | 删除本人资料后跑清理 | 各集合、附件引用、回应字段及新增缓存不残留原用户贡献 |
| P03 | 当前隐私未同意直接调用写接口 | 文本不进入内容安全处理或业务库 |
| C01 | 旧四种类型混合两种新类型 | 首页、历史、导出、规则处理均正确，无 unknown-kind 崩溃 |
| C02 | 关闭新功能开关 | 禁止新建，旧记录继续可读/导出/删除 |
| U01 | 小屏、大字体、键盘弹起、双手机往返 | 主操作可达、正文可读、无横向溢出、无误丢草稿 |

真机至少使用两个不同微信账号完成感谢发送/轻回应、单方/双方周回顾、重新进入、失网重试；第三个账号验证越权。隐私删除演练使用专门测试空间，不清空要用于分析的既有内测空间。

## 9. 内测指标与埋点

这些是待验证的行为指标，不是疗效或婚姻质量指标。第一批不预设无依据的转化率目标，先记录基线、分子分母和样本数。负担反馈通过自愿访谈或独立问卷收集，本期不新增小程序反馈表单；受访者知道反馈不会发给伴侣，拒绝反馈不影响使用。

| 指标 | 口径 |
|---|---|
| 感谢使用率 | 一周内至少发布一条感谢的有效空间 / 当周至少一次打开产品的有效空间 |
| 双方正向参与空间数 | 一周内两位成员各自至少发布一条感谢，或一方感谢被另一方自愿轻回应的去重空间数；分开报告两种路径 |
| 周回顾参与率 | 在完整发布窗口内至少一方发布回顾的空间 / 有资格且看过该周入口的空间 |
| 次周双人使用率 | 首周完成双人有效互动、且观察期完整的空间中，次周双方均有主动业务操作的比例；不把后台同步当主动操作 |
| 负担反馈 | 自愿反馈“轻松/一般/有负担”，分别记录双方答案，不在伴侣页面展示个人反馈 |

最小事件：gratitude_entry_viewed、gratitude_submitted、gratitude_acknowledged、weekly_review_viewed、weekly_reflection_submitted、weekly_prompt_dismissed。曝光在同一会话去重，写入成功以服务端为准。失败只记录粗粒度错误码与版本，不记录输入正文。分析键使用隔离的去标识化空间/成员键，留存期限在正式隐私材料中明确，不能默认为永久分析保存。

## 10. 发布顺序及完成定义

1. 先完成兼容读取、领域约束、事务/隐私/契约测试，再开放任何新写入。
2. 第一小版本上线感谢记录、轻回应、历史展示及完整隐私生命周期。
3. 第二小版本上线周期计算、周回顾编辑/阅读、摘要及历史。
4. 新功能按测试空间开关启用；保留原加减分与调分回归测试。
5. 10–20 对自愿伴侣内测至少两周，分别收集双方是否愿意继续用、是否有压力；不要求上传关系截图作为反馈。

交付完成必须同时满足：自动化测试通过、构建通过、两账号真机验收通过、退出/删除/旧版兼容通过、文案与隐私说明同步。仅写完页面、仅本地测试或仅云函数返回 200 都不算完成。
