# AI 内容审阅台设计

日期：2026-07-02
状态：已确认

## 1. 背景

Hermes 内容工作流已经能够每天检索、筛选并生成以下文件：

- `out/final/*.json`：母稿以及公众号、小红书、今日头条、知乎四个平台正文
- SQLite `publish_queue`：文章生成和人工审核状态

当前主要问题不是内容缺失，而是 JSON 不适合人工审阅。用户无法直观看到 Markdown 的发布排版，也不方便在不同平台版本之间切换、修改和复制。

服务器环境为腾讯云 Lighthouse Ubuntu 4 核 8 GB。用户希望通过电脑或手机随时访问审阅台，但暂时没有可用于 HTTPS 的自有域名。

## 2. 目标

第一版提供一个轻量、可编辑、可恢复的浏览器审阅台：

1. 以接近发布结果的形式渲染 Markdown。
2. 在同一页面切换母稿和四个平台版本。
3. 在线编辑标题、栏目和正文。
4. 手动保存，每次保存自动生成历史版本。
5. 支持复制正文、标记通过、标记退回和恢复历史版本。
6. 通过有效 HTTPS 和应用登录保护公网入口。
7. 复用现有 JSON、SQLite 和部署目录，不引入第二套内容数据库。

## 3. 非目标

第一版不包含：

- 自动登录或自动发布到内容平台
- 完全复刻微信公众号、小红书等平台的像素级界面
- 多用户、角色、组织或复杂权限系统
- 富文本所见即所得编辑器
- 评论、协作审批流和消息通知
- 内容生成提示词管理
- 数据分析大屏

这些能力只有在日常审阅流程证明有价值后再增加。

## 4. 已确认的产品决策

### 4.1 使用方式

选择“浏览器审阅台”，而不是仅导出 Markdown 文件或维护平台拟真手机预览。

原因：

- 文章列表、平台切换、编辑、预览和复制可以集中完成。
- 电脑与手机均可使用。
- 比像素级平台模拟器更轻，更不容易因平台 UI 更新而失效。

### 4.2 编辑与保存

- 支持在线编辑。
- 不做实时自动保存。
- 用户点击“保存”后才写入内容。
- 每次覆盖前创建不可变历史快照。
- 用户可以查看和恢复任意历史快照。

手动保存减少误编辑被静默覆盖的风险；历史快照则让误操作可逆。

### 4.3 访问方式

在没有自有域名的前提下，首选 Tailscale Funnel：

- 审阅应用仅监听 `127.0.0.1`。
- Funnel 提供 `https://<name>.<tailnet>.ts.net` 公网地址和有效证书。
- 应用本身继续要求账号密码。
- 腾讯云防火墙无需开放审阅应用端口。

Tailscale Funnel 当前仍为 Beta。部署时必须验证腾讯云服务器和用户所在网络的实际可用性。若访问不稳定，则切换到：

1. Tailscale Serve，仅允许安装 Tailscale 的个人设备访问；或
2. 后续购买域名并使用标准反向代理和 HTTPS。

参考：

- <https://tailscale.com/docs/features/tailscale-funnel>
- <https://tailscale.com/docs/features/tailscale-serve>

## 5. 界面设计

### 5.1 桌面布局

页面分为三个主要区域：

1. **文章栏**
   - 按创建时间倒序显示文章。
   - 展示标题、栏目、创建时间和审核状态。
   - 可按“待审核、已通过、已退回”筛选。

2. **内容区**
   - 顶部标签：母稿、公众号、小红书、今日头条、知乎。
   - 编辑模式采用左右分栏：左侧 Markdown 编辑器，右侧实时预览。
   - 标题和栏目位于正文上方。

3. **操作区**
   - 保存
   - 复制当前平台正文
   - 标记通过
   - 标记退回
   - 历史版本

未保存内容存在时，离开文章或刷新页面应触发浏览器确认。

### 5.2 手机布局

- 文章栏折叠为抽屉。
- 编辑与预览通过按钮切换，不强行左右分栏。
- 保存、复制和审核按钮固定在页面底部。
- 不追求平台界面的像素级模拟，只保证标题、段落、列表、引用、分隔线和链接可读。

### 5.3 状态与反馈

- 保存成功后显示时间和版本号。
- 复制成功后提供短暂提示。
- 质量问题显示为警告，不静默吞掉。
- 网络或保存失败时保留编辑器内容并明确显示错误。
- 历史恢复是一次新的保存，不删除恢复之后的版本链。

## 6. 技术方案

### 6.1 方案比较

#### 方案 A：Flask + 服务端模板 + 原生 JavaScript

优点：

- 与现有 Python 项目和 SQLite 直接集成。
- 资源占用低，4 核 8 GB 足够。
- 登录、会话、API、编辑器和版本逻辑可控。
- 无需 Node 构建链。

缺点：

- 需要自行维护少量前端交互。
- 需要新增 Python Web 依赖。

#### 方案 B：Streamlit

优点：

- 原型速度快。

缺点：

- URL、会话、编辑状态和移动端交互不够可控。
- 登录与版本恢复会逐渐变成对框架的绕行。

#### 方案 C：前后端分离 SPA

优点：

- 长期交互扩展性最高。

缺点：

- 引入构建链、静态资源部署和更多依赖。
- 对当前单用户审阅问题属于过度设计。

### 6.2 选择

采用方案 A：

- Flask 提供页面、登录和 JSON API。
- Gunicorn 运行单进程多线程服务，减少 SQLite 写并发复杂度。
- 原生 JavaScript 管理文章切换、编辑、预览和保存。
- `markdown-it-py` 在禁用原始 HTML的模式下渲染 Markdown，避免生成内容注入脚本。
- 不使用 CDN，前端资源随项目一起部署，避免公网资源不可达导致页面失效。

### 6.3 模块边界

建议新增：

```text
ai_content_loop/
  review/
    __init__.py
    app.py          # Flask 应用工厂与路由
    auth.py         # 登录、会话、CSRF、限速
    repository.py   # JSON、历史快照和 SQLite 状态
    templates/
      login.html
      review.html
    static/
      review.css
      review.js
deploy/
  systemd/
    ai-content-review.service
```

现有生成逻辑不依赖 Web 层。审阅台可以停止或升级而不影响每日内容生成定时器。

## 7. 数据设计

### 7.1 正文的唯一事实源

`out/final/*.json` 继续作为正文的唯一事实源，保留现有结构：

```json
{
  "dedupe_key": "...",
  "column": "...",
  "master_title": "...",
  "master_markdown": "...",
  "platform_markdown": {
    "wechat": "...",
    "xiaohongshu": "...",
    "toutiao": "...",
    "zhihu": "..."
  }
}
```

审阅台不复制正文到 SQLite，避免 JSON 与数据库出现两个互相冲突的版本。

### 7.2 审核状态

`publish_queue.status` 使用：

- `needs_human_review`
- `approved`
- `revision_requested`

状态变更不自动发布，也不自动重新调用 Hermes。

### 7.3 历史版本

历史文件布局：

```text
out/history/<安全文章标识>/<UTC时间>-<版本摘要>.json
```

每个快照包含：

- 完整正文 JSON
- 保存时间
- 操作类型：`edit` 或 `restore`
- 上一个版本摘要

历史目录只允许审阅应用写入，普通页面请求不能构造任意路径。

### 7.4 保存事务

一次保存按以下顺序执行：

1. 根据服务器维护的文章映射定位目标文件，拒绝客户端文件路径。
2. 校验 JSON 字段、平台集合、字符串类型和最大长度。
3. 重新运行基础内容质量检查。
4. 保存当前文件的历史快照。
5. 将新内容写入同目录临时文件并刷新到磁盘。
6. 使用原子替换覆盖目标文件。
7. 返回新版本摘要和质量警告。

若第 2 至第 5 步失败，原文件保持不变。

为避免两个浏览器标签相互覆盖，加载文章时返回版本摘要；保存时必须携带该摘要。摘要已变化则返回冲突，不覆盖新版本。

## 8. API 草案

所有变更接口都要求登录和 CSRF Token。

```text
POST /login
POST /logout

GET  /api/articles?status=needs_human_review
GET  /api/articles/<dedupe_key>
PUT  /api/articles/<dedupe_key>

GET  /api/articles/<dedupe_key>/history
POST /api/articles/<dedupe_key>/restore/<version>

POST /api/articles/<dedupe_key>/status
```

正文 API 不接受服务器路径。文章标识经过 URL 编码后只用于数据库查询，再由服务器解析真实文件。

## 9. 安全设计

### 9.1 凭据

- 用户名和密码不进入 Git。
- 密码以强哈希形式保存在服务器权限受限的环境文件中。
- Flask 会话密钥独立随机生成。
- 启动时缺少密钥或密码哈希则拒绝启动。

### 9.2 会话

- Cookie：`Secure`、`HttpOnly`、`SameSite=Lax`。
- 会话空闲超时。
- 登录后重新生成会话状态。
- 所有写操作验证 CSRF Token 和同源请求。

### 9.3 登录保护

- 登录失败按来源 IP 限速。
- 错误信息不区分用户名或密码错误。
- 日志不记录密码、Cookie、正文全文或密钥。

### 9.4 内容安全

- Markdown 渲染禁用原始 HTML。
- 模板默认转义。
- 外部链接使用安全属性。
- 设置内容安全策略和禁止 MIME 嗅探等响应头。

## 10. 部署设计

### 10.1 文件与用户

- 代码：`/opt/ai-content-loop/repo`
- 配置：`/opt/ai-content-loop/config.toml`
- 输出：`/opt/ai-content-loop/out`
- 服务用户：`agentuser`
- Web 服务监听：`127.0.0.1:8765`

### 10.2 systemd

新增独立长驻服务：

```text
ai-content-review.service
```

职责：

- 读取服务器环境文件。
- 使用 Gunicorn 启动 Flask。
- 异常退出自动重启。
- 只监听回环地址。

每日生成服务和审阅服务相互独立。

### 10.3 Funnel

部署时：

1. 安装并登录 Tailscale。
2. 启用 HTTPS 和 Funnel。
3. 将 Funnel 目标指向 `127.0.0.1:8765`。
4. 验证公网 URL、登录、保存、恢复和退出。
5. 不在腾讯云安全组开放 `8765`。

## 11. 测试策略

### 11.1 单元测试

- 安全文章标识和路径限制
- JSON 校验
- 快照创建
- 原子保存
- 版本冲突
- 历史恢复
- 状态变更
- 密码校验
- 登录限速
- CSRF 校验

### 11.2 Web 集成测试

- 未登录访问跳转到登录页
- 正确和错误登录
- 文章列表和详情
- 编辑保存后 JSON 正确更新
- 保存失败时原文件不变
- 恢复历史产生新版本
- 非法文章标识不能读取服务器其他文件
- 未带 CSRF 的写请求被拒绝

### 11.3 部署验收

- `ai-content-loop` 每日定时任务继续正常运行。
- 审阅服务只监听 `127.0.0.1`。
- 公网 Funnel URL 使用有效 HTTPS。
- 未登录不能读取正文。
- 手机和电脑均能编辑、预览、保存、复制与退出。
- 重启服务器后审阅服务和 Funnel 配置仍可用。

## 12. 风险与回退

| 风险 | 应对 |
|---|---|
| Tailscale 在当前网络不可用 | 切换 Serve；后续购买域名 |
| Funnel Beta 行为变化 | 服务保持本地监听，入口可替换而无需修改业务代码 |
| 用户误覆盖内容 | 手动保存、版本摘要冲突检测、历史恢复 |
| 生成任务和审阅同时操作同一文章 | 原子替换；审阅保存前校验版本摘要 |
| Markdown 注入危险 HTML | 渲染时禁用原始 HTML |
| SQLite 写锁 | Gunicorn 单进程；事务短小；设置合理超时 |

## 13. 第一版验收标准

第一版完成的定义：

1. 用户能从 HTTPS 地址登录。
2. 用户能查看现有两篇及后续自动生成的文章。
3. 用户能切换母稿和四个平台版本。
4. Markdown 编辑与预览可用。
5. 保存会更新原 JSON 并生成历史快照。
6. 历史版本可以恢复。
7. 用户能复制正文并修改审核状态。
8. 所有测试通过，现有内容生成测试不回归。
9. 服务部署在 Lighthouse，重启后自动恢复。
