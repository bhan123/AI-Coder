# Signal Forge 复盘与诊断中心：第一版建议

状态：用户已批准开发，第一阶段进行中；不是已全部实现。日期：2026-09-07。进度见 `../DEVELOPMENT_STATUS.md`。

## 目标与边界

回答三个问题：预警后发生了什么，哪些环节存在可定位的问题，候选改进能否减少问题而不损害其他信号。

第一版优先盘中预警，V1 在同一中心独立统计，不能混合两种策略的结果口径。保留现有选股规则和公网入口，不自动调参，不自动交易。已有历史数据只做有证据的补录；不可恢复的字段标为未知，不伪造当时上下文。

## 已核对的现状

- `alert_events` 已按策略、交易日、股票合并，保存首次价格、末次价格、累计入选次数及极值。
- `alert_event_points` 保存预警后采样轨迹，`strategy_runs` 和 `strategy_signals` 保存运行版本和已展示信号的因子。
- 触板目前使用 9.8% / 19.8% 近似阈值；扫描器在 14:57 后可将事件终结，不能视为收盘行情确认。
- 每轮只保存前三名信号；完整候选、各条件是否通过、排名落选与不符合规则没有完整留档。
- 目前没有正式发布时刻、完整参数快照及每个行情字段的源时间，旧数据不足以完整还原用户当时可见的信息。

## 1. 统一复盘账本

新增独立模块，不把报告逻辑继续堆入行情扫描循环。

每个事件关联：原始 run、股票和交易日、策略和代码版本、参数快照、首次触发快照、实际发布时间、后续轨迹、收盘证据、次日结果、数据完整度。保留原始数据，衍生结论记录计算版本。

主统计单位为同一策略下的“股票＋交易日”的首次正式预警；重复提醒不扩大分母。若同日切换策略配置，标为混合版本，不能直接计入单一版本对照。再次触发或第三次确认属于另一个研究观察点，必须从那个时刻重新计算后续表现。

价格、源行情时间、抓取起止时间、策略决策时间和发布成功时间分别存储。旧数据没有发布时刻时，只报告“记录时刻后的市场表现”，不称为用户可执行收益。

## 2. 成功口径与统计保护

预警目标是观察未来触板，不设置一个混淆多种结果的总胜率。

| 主指标 | 定义 | 必要证据 |
| --- | --- | --- |
| 预警后触板率 | 首次预警之后，发生触及真实涨停价的事件占比 | 当日证券交易规则、真实涨停价、能够确定先后顺序的行情 |
| 收盘封板率 | 正式收盘价处于当日涨停价的事件占比 | 正式收盘行情与当日真实涨停价 |
| 收盘高于预警价比例 | 正式收盘价大于首次预警参考价的事件占比 | 首次参考价与正式收盘价；只是价格表现，不是交易盈利率 |

辅助指标：从首次预警到收盘的变化均值、中位数、分位数，以及预警后最大有利/不利变化。最低价相对首次价的跌幅命名为“最大不利变化”，不误称峰谷最大回撤。次日固定时点结果独立呈现；若要评价交易收益，需要另行固定入场、退出、成本和可成交假设。

每个指标展示分子、有效分母、未知数和覆盖率。没有足够证据的事件既不计成功，也不计失败；同时展示全部事件规模，避免通过排除缺失样本美化结果。零预警日、扫描失败日、休市日和待收盘日必须区分。

仅有两分钟采样时，显示“采样观测到触板”，不冒充完整触板率。全天最高价等于涨停价不能证明触板发生在预警后；如果时间顺序无法还原，应为未知。

5 / 15 / 30 / 60 分钟后的变化可作诊断，但必须使用固定交易分钟、明确午休和收盘边界，未成熟或超出允许采样误差的观察点不填充结果。

历史分组优先使用首次预警时已经知道的版本、时段、交易板、规则分、板块和市场状态；不能用当日最终最高分或最终累计次数解释首次预警时能否作出更好决策。置信度按交易日相关性处理，小样本不出“稳定有效”排名。

## 3. 问题定位：事实、关联假设、未知分开

| 类别 | 可检查的内容 | 输出边界 |
| --- | --- | --- |
| 数据与工程 | 行情过期或缺失、价格与涨幅冲突、跨午休复用快照、重复计数、发布延迟、任务失败 | 有原始时间与数据证据时，可标为确认问题 |
| 信号与环境 | 触发时距涨停过近、短期拉升后衰减、板块或市场同步转弱、评分与后续表现不一致 | 先标为关联现象或待验证假设，不宣称因果 |
| 结果形态 | 未触板、触板后开板、收盘低于首次价、次日走弱 | 属于结果分类；可以同时出现，不自动等同策略失效 |
| 无法归因 | 所需历史量能、公告时间、候选上下文无法恢复 | 标为证据不足，不能由模型补写事实 |

每条问题记录包含：问题 ID、影响事件、发生时刻、原始证据链接、检测规则版本、事实描述、假设、可能影响、拟议改进、验证状态。多标签允许重叠；报告中的标签占比不强制相加为 100%。

点击股票可看三个小节：为什么被选中、之后发生什么、哪些问题有证据。图表、分数与失败标签均能回到同一事件账本。

## 4. 如何减少重复问题

确认的工程问题通过回归测试防止复发。策略机制问题走受控实验：

1. 报告提出可检验假设与可能副作用。
2. 固定候选规则和比较指标，保留原策略。
3. 在相同时点、股票池和行情条件下并行记录候选策略，先不改变用户收到的预警。
4. 用后续新交易日比较触板、收盘表现、预警数量、漏掉的成功事件及亏损尾部。
5. 经确认后再切换策略；保留版本和回退入口。

不能用同一批失败股票找阈值，再用这批股票宣称验证成功。过滤掉的候选需留轻量账本并跟踪，否则无法衡量漏报代价。仅有已预警事件时，只能评价这批事件的后续表现，无法可靠计算全市场召回率。

## 5. 定期报告与网页

建议入口：复盘中心，下分“效果总览 / 报告归档 / 问题库”。已有每日信号保持 V1 置顶，股票详情仍在对应行下展开。

建议排期（待用户确认）：

- 每个交易日北京时间 16:30：日报，包括当天预警结果、数据覆盖、异常和代表性案例。
- 每周五北京时间 18:00：周报，包括整体变化、按版本和时段分层、反复出现的问题、下周待验证假设。
- 次日结果补齐时：新增对应报告修订版，明确原观察期和更新时间，不覆盖先前结论。

以上为产品服务器端任务方案，不创建依赖桌面开机的提醒。使用现有服务器调度体系，任务独立于两分钟扫描与 14:50 采集。正式排期启用前需验证数据源收盘就绪时间、交易日历与当前部署权限。

报告必须包括观察区间、截止时刻、策略/统计版本、分子分母、覆盖率、数据缺口和来源。缺收盘行情时发布明确标识的“不完整报告”，排队重试；零预警也出报告。任务失败在页面显示，不把失败写成无预警。

日报结构：一句结论 → 主要指标和覆盖率 → 分层表现 → 正反案例 → 已确认问题 → 待验证假设 → 后续动作。

报告留档应保存结构化 JSON 和可阅读页面，按周期、策略版本及计算版本幂等生成；数据补齐产生新 revision。网页展示生成状态、最后成功时间与下一计划时间。

## 6. 大模型的边界

确定性程序计算数字和规则标签；大模型可选地整理证据、归纳案例、提出实验假设。模型输出必须能引用事件或资料，不独自计算正式成功率、不把猜测写成已确定原因、不自动修改筛选规则。

第一版不用外部模型也能完成统计、报告和工程诊断。后续接入时，只分析候选和摘要，缓存同一资料；模型失败不影响预警、指标和日报。社区与新闻只在有合法可用来源、采集时间和发布时刻证据后纳入。

## 7. 测试驱动实施顺序及验收

1. 账本与结果计算：一条真实路径贯通事件、结果、指标；验证重复运行不多计、未知不计失败、先后顺序与不同交易板边界。
2. 收盘对账与报告：验证迟到数据、失败重试、零预警日、非交易日、报告修订和计算可重现。
3. 问题证据链：验证数据异常检测与每条问题跳转，明确排名落选不等于条件失败。
4. 网页入口与服务器排期：验证筛选、排序、行内展开、数据不足提示；新任务不阻塞现有任务。
5. 对照实验：验证仅使用当时可用输入、同批公平比较和独立未来观察期，再讨论调参。

每一阶段按一个行为测试失败、最小实现通过、回归的顺序推进。上线前备份、构建验证、检查固定入口及定时采集；目前尚未创建产品日报/周报服务器任务、修改生产数据或启用任何新规则。
