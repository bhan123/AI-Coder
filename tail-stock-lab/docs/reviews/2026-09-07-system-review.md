# Signal Forge 系统与策略评估

评估日期：2026-09-07。范围：当前本地代码、线上运行状态与只读数据库统计；未修改策略、配置、定时器或生产数据。9 个核心文件的本地与远端源码 SHA-256 一致。

## 核心判断

系统已具备持续采集、定时选股、预警归档与次日复盘的基础。下一阶段的首要投入应是让结果可核验、让实验可比较，再扩展策略与大模型。现有数据尚不能证明两种策略具有稳定的交易收益优势。

当前结构中值得保留的部分：行情适配器与策略计算分离；信号保存因子解释与策略版本；正式定时记录与手动运行区分；盘中预警服务独立于尾盘采集服务；V1 优先运行，其他策略异常有独立处理。

目前规模适合继续采用模块化单体与 SQLite，重点是明确任务边界、数据契约、事务和配置来源。暂未看到必须引入微服务、消息集群或更大服务器的证据。

## 1. 最近运行与表现：先统一口径

实测固定公网入口 `/health` 返回 HTTP 200；容器已连续运行约三周；预警服务、14:50 采集及 10:35 次日结果定时器均 active。策略版本为 V1 1.1.0、预警 0.2.0。

### 两个特别容易误读的现象

- 79 个累计入选至少 3 次的事件中，70 个在两次入选之间存在未入选观测点。现有“连续增强次数”实际上是累计入选次数，而且受每轮只保存前三名影响。未入选也可能仅是排名下降，不能直接解释为个股转弱。
- 累计入选至少 3 次的组最后观测平均变化为 +0.771%，不足 3 次组为 -0.895%。这是事后分组，首次预警时尚不知道最终会入选几次。如果研究“等第三次再提醒”，必须从第三次触发后的可用价格重新计时和计算结果。

### 其他应随工程整理完成的改进

- `record_alert_run` 重放同一个 run 仍增加累计次数，尽管明细点有唯一键。此次样本未发现计数不一致，但重试/回放路径缺少幂等保障；用事件键或唯一 run 处理记录保证重放不重复计数。
- 行情失败目前主要写日志，不能在历史里区分“任务失败、数据不足、成功但零预警”。8 月 19 日、9 月 2 日确有扫描却没有事件，历史日期来源是事件表，因此日期选择器会漏掉这些零预警日。
- SQLite 当前 journal_mode 为 delete；应用连接未显式开启外键。建议结合并发写入场景验证 WAL、显式事务、外键和 busy timeout；迁移与补历史不应依附于每次 Repository 构造。
- 已隐藏的 P1–P4 仍参与每次正式尾盘任务；建议增加 enabled/shadow/disabled 状态，研究策略与正式策略明确分流。是否停用属于后续实施选择。
- P4 把分钟成交量变化当“封单变化”、把换手与强弱代理写作“资金承接”，没有真实委托队列证据。后续即使恢复 P4，也应先修正名称和数据契约。
- 上线流程应使用完整、可追溯的发布物，包含依赖锁定、版本号、健康检查和可回滚镜像；当前后端依赖大量使用 `>=`，重建可能改变运行依赖。
- 当前项目未被父 Git 仓库跟踪，测试目录还留有 603 个临时 SQLite 文件（约 34.2 MB）。建立独立版本管理/CI、临时文件夹与清理策略，避免源码、数据、备份进入同一个部署上下文。本次未删除文件，也未查看部署备份的内容。

## 3. 两种策略如何优化

### V1：先验证“止跌”，再讨论分数高低

代码只使用截面数据，`requires_intraday=False`。价格高于日内最低价 0.3% 并不能确认当前正在回升：上午形成低点、午后再次走弱也可能满足。策略名中的“止跌”和实际证据之间有缺口。

建议将以下改动作为候选实验逐一验证：

1. 增加最后 10–15 分钟不创新低、低点逐步抬高、收回局部 VWAP/关键位置等时间序列证据。
2. 区分随市场/板块下跌后的反弹与公司独有利空；重大风险公告作为独立风险标签。
3. 相对强度同时参照市场与所属板块，并按波动水平比较，避免用同一绝对跌幅代表所有股票的“恐慌程度”。
4. 测试缩量回踩、反弹成交额、成交活跃度是否提供增量价值。现有量比/换手可保留为基线。
5. 同时报告次日开盘、固定观察时点、规则退出、正式收盘、最差不利波动，避免单一退出规则掩盖信号本身特性。

上线之前要与现有 V1 在同一批时点、同一股票池、同一结果口径下比较。建议按市场状态分层，同时观察信号数量和亏损尾部，不能仅优化胜率。

### 盘中预警：检验“继续走强”的增量信息

新版涨停进度与最近三点增强方向正确，但规则仍主要对当前涨幅、累计量比、换手和行业涨幅打分。较高涨停进度本身就得到更多分数，可能让晚出现的强势股更容易进入前三；这不等于从提醒时刻开始有更好的后续空间。

建议优先实验：

1. 将“观察”与“确认”分为两个阶段。观察记录异动，确认要求关键位突破后保持或回踩成功；分别记录各自价格和效果。
2. 近期增量成交额/量能、离均价线距离、日内高点回撤、价格斜率替代部分累计强度的重复加分。具体阈值应由后续样本验证。
3. 行业上涨比例、近期同向增强比例与板块成交占比变化比绝对“至少 3 家上涨”更可比较；大行业有 3 家上涨的含义很弱。
4. 主板、20% 交易板及开盘/午后分开评估；市场退潮开关加入上涨广度变化、强势股回落、板块同步走弱等动态证据，先验证再上线。
5. 保存完整合格候选的轻量因子记录，并把“用户只看前三”作为展示决策。否则难以回答被排除的股票是不是表现更好。
6. 为已预警股票设置状态：观察、确认、持续符合、失效、触板、收盘确认。只有新事件或状态升级才推送，允许冷却与重新触发。

收益评估要以用户实际能行动的时刻为基准。普通 A 股买入后存在交收前卖出限制，因此当日冲高并不等于可以锁定利润；规则依据见[上交所现行交易规则](https://www.sse.com.cn/lawandrules/sselawsrules2025/stocks/exchange/c/c_20260424_10816482.shtml)。系统只做预警时，也应把信号后市场表现与模拟执行结果分别标清。

## 4. 最值得新增的能力

| 建议顺序 | 能力 | 直接解决什么问题 |
| --- | --- | --- |
| 1 | 统一复盘账本 | 每条信号关联真实触发时点、官方收盘、次日观察及数据完整度，形成可信结果基线 |
| 2 | 每轮筛选诊断 | 看见总股票数、有效行情数、各门槛剔除数、最终合格数和展示数；零预警时能够解释原因 |
| 3 | 策略对照实验 | 保存参数/代码版本，同步运行基线和候选，按时间向前验证；记录每个新因子的增量作用 |
| 4 | 信号生命周期与提醒 | 页面自动刷新，新信号/升级/失效提醒，减少靠刷新网页盯盘 |
| 5 | 市场状态与板块地图 | 显示上涨广度、板块强弱和退潮变化，解释当天策略环境 |
| 6 | 事件与社区情绪辅助层 | 补充规则没有覆盖的新闻、公告、题材与讨论信息，评估是否改善候选排序 |

实验基础建议保留：真实信号时刻输入、决策时可用的因子、未入选候选、实际发布延迟、配置快照。当前盘中全市场原始快照只驻留内存，事后无法完整重跑不同策略。可先保存候选池与市场/板块聚合特征，按留存需求选择全市场压缩快照，无需直接上逐笔数据仓库。

评分应标为“规则分”；只有积累足够样本、完成时间外检验与概率校准后才适合显示成功概率。置信区间与收益评估按交易日/板块相关性处理，不能把同日多股当完全独立事件。

## 5. 大模型建议如何接入

建议入口是事件理解与证据整理：先读公司公告、交易所信息和可靠新闻，提取事件类型、首次发布时间、关联股票/板块、是否存在风险信息；再分析社区讨论增速、去重后的参与人数、观点分歧和价格表现是否背离。

输出应为结构化字段加可回查来源，例如催化类型、消息新颖性、证据强度、主题相关性、风险事件与情绪分歧。每条信息保存发布时间和首次采集时间，只有当时已知的内容可以进入决策。

成本控制可用候选池触发、相同事件缓存、增量抓取，模型异步处理；模型失败时保留基础规则结果并显示辅助分析不可用。把模型输出先并行记录，暂不影响原提醒；用未来新产生的数据比较“基础规则”与“基础规则加文本因子”。

不能仅把社区看多情绪直接转成加分，也不能用模型现在看到的新闻重新解释历史信号并称为回测提升。LLM 的训练数据可能包含待测历史结果；相关方法风险见 [Glasserman 与 Lin 的原始研究](https://arxiv.org/abs/2309.17322)。该研究说明评价风险，不证明本系统接入情绪后一定有效。

## 6. 回测与发布的验收边界

现有 `backend/scripts/backtest_history.py` 使用当日收盘价/最低价构造标为 14:30 的截面，默认换手率 2.0、量比 1.5，且使用当前股票池回看历史。该脚本的结果不能作为真实盘中策略有效性的证据。它与线上保存实际快照的 T+1 规则复盘是两条不同路径，后者不能因此一概否定。

建议验收测试覆盖实际行为：

- 配置更新跨进程与重启一致；无效类型、负数、零分母及冲突边界被拒绝。
- 午休、断网、缺股票和重复快照不能伪装为连续三轮确认。
- 相同 run 重放两次不增加预警次数；任务重试不重复生成正式记录。
- 收盘对账正确区分盘中采样触板、确认收盘封板、证据不足。
- 行情缺失与成功零信号在页面和历史中不同；零信号日仍可选择。
- 未显示的研究策略不阻塞主策略；图表补采失败可恢复。
- 前端自动接收新结果并提示数据过期；每条信号保存版本与配置。
- 策略候选实验只使用决策时已可获得的数据，按未来时间段检验。

推荐实施顺序：配置/接口与运行状态 → 连续计数和收盘复盘口径 → 时间数据质量与补采 → 策略对照实验 → V1/预警候选改进 → 大模型事件与情绪辅助。
